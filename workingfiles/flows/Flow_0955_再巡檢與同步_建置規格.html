核心觀念：① 所有運算式一律用 fx 插入成紫色 chip，不要直接打字（否則被當字串）。② 清單中文欄的內部名是 field_N，運算式只用內部名：field_1 員工編號／field_2 日期／field_3 Email／field_4 姓名／field_5 方案名稱／field_6 任務名稱／field_7 表單回覆／field_8 實際出勤狀態／field_9 DateString；主欄維持 Title。③ 時間一律 addHours(utcNow(),8)（台北 UTC+8），不要用 convertFromUtc（環境不一定支援）。④ 本流程會刪資料，動手前務必先看本頁最後的「待確認（PO 裁示）」。

0. 這支流程要做的事

觸發約 09:55（Line 約 09:45 發出後 10 分鐘，留給員工回覆與改 Planner 的緩衝）。目的：以「最新一次更新」為準，把員工的「表單回覆」與 Planner 的當前實際狀態同步回清單 AttendanceHistory。

做法：① 重新掃描 Planner 取得「目前仍逾期」的任務 id 集合（手法照 0930）。② 讀取清單今天的延遲列（排除占位列）。③ 逐列依「表單回覆 × 是否仍逾期」決定處置（刪列／保留／收斂）。

5. 讀清單今日延遲列

5-1 取得清單項目（SharePoint）

  1. SharePoint → 取得項目，命名 取得清單項目：站台 PLANNER_CK、清單 AttendanceHistory。
  2. 篩選查詢（Filter Query）：清空 → 點 fx → 貼整段（變紫色 chip，欄位內不要再打字）： 
    concat('startswith(Title,''', formatDateTime(addHours(utcNow(),8),'yyyyMMdd'), '_'')')
    會算出 startswith(Title,'20260622_')（'' 是跳脫單引號）。Top Count 5000。

只用 Title 做 $filter：Title 內部名固定為 Title、ASCII 安全；中文欄／改名欄的 OData $filter 會報「欄不存在」。日期一律靠 Title 前綴篩，不要對 field_2／field_9 下 $filter。

欄值

6. 逐列比對與處置

Apply to each，命名 Apply_to_each_列，來源 @body('今日延遲列')。迴圈項＝清單物件（不是字串），所以裡面引用欄位是 items('Apply_to_each_列')?['field_7']、...?['Title']、...?['ID'] 這種寫法。

6-1〔取本列任務 id〕Compose

命名 本列任務id，值（fx）。Title 格式為 yyyyMMdd_email_任務id，但 email 內含 _、任務 id 也可能以 _ 開頭，所以不能用固定 split index。建議：用 last(split(...)) 取最後一段：

last(split(items('Apply_to_each_列')?['Title'], '_'))
風險（標待確認）：若任務 id 本身含 _ 或以 _ 開頭，last(split(...,'_')) 會只取到尾段、切錯。更穩的替代：不從 Title 取 id 再 equals，改直接用「整體包含比對」——對重掃逾期集合做 contains(string(variables('仍逾期TaskIds')), 本列任務id) 仍有子字串誤判風險。最穩做法見 6-2 的建議。請 PO／你確認任務 id 的實際字元規則後定版。

6-2〔判斷本列是否仍逾期〕Compose

命名 本列仍逾期，值（fx）。最穩的判斷是「重掃逾期集合是否含本列任務 id」。因為 仍逾期TaskIds 是完整 task id 字串陣列，用陣列 contains（精確比對整個元素，不是子字串）最安全：

contains(variables('仍逾期TaskIds'), outputs('本列任務id'))
為何用陣列 contains 而非字串 contains：陣列 contains(array, value) 比對「整個元素相等」，不會把 abc 誤判進 abcd。前提是 本列任務id 真的等於 Planner 回傳的完整 id（取決於 6-1 的切法是否正確）。若 6-1 切不乾淨，這裡才會出錯——這也是 6-1 標待確認的原因。

「不再逾期」＝該 task 不在重掃逾期集合：可能是員工已勾完成（percentComplete=100）、或到期日被改到未來——兩種都會讓它退出逾期集合，符合「比照已完成」的意圖。

6-3〔依表單回覆處置〕Switch

加 Switch（切換），開關值（fx）：items('Apply_to_each_列')?['field_7']（field_7＝表單回覆）。

Case（等於）動作
1（已完成）刪除項目（SharePoint）：清單 AttendanceHistory；項目 ID（fx）items('Apply_to_each_列')?['ID']
2無動作（保留）。可放一個 Compose 註記「保留：2」便於追蹤。
3無動作（保留）。
4（其他）放條件：@equals(outputs('本列仍逾期'), false)。
　• 是（不再逾期） → 刪除項目（ID 同上）＝比照已完成。
　• 否（仍逾期） → 收斂 2/3：更新項目 待確認（見待確認清單，目前不要自動硬寫 2 或 3）。
預設（Default）無動作（空白＝員工尚未回覆，保留待人工／隔日）。
刪除項目要用整數 ID，不是 Title：SharePoint「刪除項目」的「Id」欄要填清單項目的整數主鍵，也就是「取得項目」回傳的 ID 欄（items('Apply_to_each_列')?['ID']），不是 Title 字串。填 Title 會刪不掉或報錯。

7. 待確認（PO 裁示）

以下四點規格模糊或具破壞性，我不自行發明，列出選項請 PO 裁示後再定版：

① 回覆=4 且「仍逾期」要收斂為 2 還是 3 — 自動分不出

  • 問題：2＝「已到公司在補進度」、3＝「沒到公司·填假卡」，差別是員工是否到公司，這資訊 Planner／清單裡沒有，自動化無從判斷。
  • 建議（擇一）：
    1. 不自動改，保留原回覆 4＋在 field_8 或備註標「待人工」，由行政在頁簽決定 2/3。（最安全，我建議這個）
    2. 一律收斂為 3（沒到公司·假卡），偏保守。
    3. 一律收斂為 2（補進度中），偏寬鬆。
    4. 不收斂，原樣保留 4，視為「未結案」隔日人工跟。

② 自動「刪除清單列」具破壞性 — 是否改為較安全替代

  • 問題：流程自動硬刪資料，誤判（例：任務 id 切錯、Planner 暫時讀不到、員工誤點 1）就救不回。
  • 替代方案與 trade-off：
    方案做法trade-off
    A 真刪（規格原文）Switch 直接「刪除項目」清單最乾淨；不可逆、無稽核痕跡
    B 軟刪／標記（建議）不刪，改「更新項目」把 field_8 或新增一個「狀態」欄標成 已完成-待歸檔；步驟 7 備份流程再實際移除可逆、留痕、行政可覆核；清單當天會多保留幾列
    C 搬備份後刪先寫一份到備份 Excel／清單，再刪原列留痕＋清單乾淨；多一段寫入、較複雜
  • 我的建議：先上 B（軟刪／標記），跑穩一兩週、確認任務 id 比對零誤判後，再視需要切到 A。詳見本頁最後「自動刪列風險」段落。

③ 從 Title 取任務 id 的方法 — Title 結構有雙底線風險

  • 問題：Title＝yyyyMMdd_email_任務id，但 email 含 _、任務 id 也可能含/起頭 _，固定 index split 會切錯。
  • 建議：① 確認 Planner task id 的實際字元規則（是否純英數、是否含底線）。② 若 task id 不含底線，last(split(Title,'_')) 即可且安全。③ 若可能含底線，改用「在寫入時就保留乾淨 id」：建議 0930 寫清單時多寫一個純 id 欄（如某個 field_N），這支流程直接讀該欄做陣列 contains 精確比對，完全不靠 Title 解析（最穩，建議推這個）。④ 不建議用 contains(string(集合), id) 子字串比對（短 id 會誤中長 id）。

④「不再逾期」如何判定

  • 定義：本流程「重掃 Planner→逾期集合」後，該 task 不在集合即視為「不再逾期」。涵蓋兩種情形：(a) 已完成（percentComplete=100），(b) 到期日被改到未來。兩者都讓它退出逾期集合，符合「比照已完成」。
  • 待 PO 確認：情形 (b)「只是把到期日往後改、實際沒做完」是否也該當「比照已完成刪列」？若不希望，需要更嚴格的判定（例如：只認 percentComplete=100 才算完成），這要在重掃時另存一份「已 100% 完成」的 id 集合分開判斷。請 PO 表態是否需要區分。

8. 測試計畫

  1. 備資料：先確認清單今天已有延遲列（由 0930 寫入，或手動建幾筆），涵蓋 field_7 ＝ 1 / 2 / 3 / 4 / 空白 各至少一筆。
  2. 造對照情境：到 Planner 把其中一兩個「回覆=4」對應的任務勾完成或把到期日改到未來（讓它退出逾期集合）；另留一個「回覆=4」的任務維持逾期。
  3. 手動測試（Test → Manually）跑一次。
  4. 驗收：
    • 回覆=1 的列 → 已刪除（或軟刪標記，依採用方案）。
    • 回覆=2、3 的列 → 原樣保留、未被動。
    • 回覆=4 且任務已不逾期 → 已刪除（比照完成）。
    • 回覆=4 且任務仍逾期 → 依 PO 裁示處置（保留待人工／收斂 2/3）。
    • 回覆空白的列 → 未被動。
    • 占位列（_TaskOnSchedule）完全不受影響（已被 6-2 的篩選排除）。
  5. 邊界：① 仍逾期TaskIds 是否扁平字串陣列（展開變數輸出檢查，不可有巢狀 [[...]]）。② 本列任務id 是否＝Planner 完整 id（抽查幾列比對）。③ for_each 是否關閉並行（避免 union 掉資料）。
  6. 回歸：跑完看員工儀表板、行政頁簽資料是否一致；隔日 0930／0945 是否照常。

9. 注意彙整

  • 關閉 for_each 並行：本流程用變數 union 累積逾期 id，務必把 Planner 掃描各層 Foreach 的「設定 → 並行控制」關閉（循序），否則並行寫變數會掉資料、漏判逾期。
  • 欄位內部名是 field_N：引用清單欄一律 field_N（表單回覆＝field_7、實際出勤狀態＝field_8）；不要用中文顯示名做運算式。
  • $filter 只認 Title：當日篩選用 startswith(Title,'yyyyMMdd_')，且用 fx concat 組整段、不可手打；中文/改名欄下 $filter 會「欄不存在」。
  • 刪除要用整數 ID：刪除項目填 ID（取得項目回傳的整數主鍵），非 Title。
  • Select 文字模式 vs 物件模式：4-4 的「選取_逾期id」用文字模式，輸出是字串陣列；6 的 Apply to each 來源是清單物件陣列，迴圈項是物件、要 items(...)?['field_N']。兩者型別不同別搞混。
  • 時間二分法：清單篩選／顯示日期用 addHours(utcNow(),8)（台北）；逾期條件內與 dueDateTime 比較用 utcNow()（同為 UTC）。不要混用。
  • 本流程不發信、不發 Line、不寫 Excel：只重掃 Planner＋讀清單＋處置清單列。
  • 占位列零影響：6-2 篩掉 _TaskOnSchedule 後才進迴圈，占位列不會被刪改。

10. 對「自動刪列風險」的具體建議

建議：上線首版採「軟刪／標記」（待確認 ②方案 B），不要一開始就自動真刪。

  • 為何：本流程是否刪列，完全押在「任務 id 從 Title 解析正確」＋「重掃逾期集合完整」兩件事上。前者有雙底線切錯風險（待確認③），後者受 Planner 連線瞬時錯誤影響。任一失準，A 方案會誤刪、且不可逆、無痕。
  • 軟刪做法：Switch 命中「應刪」時，不呼叫「刪除項目」，改「更新項目」把一個狀態欄（建議新增專用欄，或暫借 field_8 但要避開行政語意衝突）標成 已完成-待歸檔；實際移除交給步驟 7 的「清單→Excel 備份」流程，在備份成功後才刪。這樣留痕、可覆核、可回滾。
  • 切換條件：跑穩一到兩週、確認 (1) 本列任務id 抽查全對、(2) 無誤刪/漏判、(3) Planner 重掃穩定，再評估切到 A（真刪）。
  • 更穩的根因修法：請 0930 寫清單時多寫一個純任務 id 欄，本流程直接讀該欄做陣列精確 contains，不靠 Title 解析——這能同時消掉待確認①③的大半風險，強烈建議優先採行。
