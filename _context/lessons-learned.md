# Lessons Learned

## 2026-07-07（行事曆全天事件用 UTC 午夜當邊界，時區換算的查詢視窗仍會撈到昨天）
- **全天事件 `timeZone:"UTC"` 時，查詢視窗用「台北當日 00:00~23:59 換算成 `+08:00` offset」會跟前一天的單日全天事件重疊 8 小時**：換算後的 UTC 視窗＝「前一天16:00～當天15:59」，跟「只請一天」的全天事件 UTC 邊界（如 07-06T00:00～07-07T00:00）重疊，導致查「今天」卻撈到「昨天」的假（實例：查 07-07 撈到 `張耀中請年假，2026-07-06(全天)`）。**06-26 陳宏錡案那次「改單日視窗」只解決了查詢範圍過寬（±1天）的粗問題，沒解決這個更細的邊界重疊**——單日視窗看似正確，實際仍有 8 小時滲漏帶，屬於同類 bug 的殘留變種，不能以為「改過一次就沒事」。
- **修法：時間參數尾碼改 `Z`（不用 `+08:00` 時區換算）**：把台北日期字面數字直接當 UTC 邊界（`concat(台北日期,'T00:00:00Z')`），視窗變成 UTC「當天00:00～23:59」，跟前一天全天事件（結束於當天T00:00）恰好不重疊；跨日事件 UTC 邊界本來就橫跨好幾天，不受影響。**這是這個特定行事曆（全天事件錨定 UTC 午夜）的專屬修法，不是「時區處理一律用 Z」的通則**——換一個行事曆若全天事件錨定的是當地時區，套用同一招會錯，動手前先用真實資料的 start/end 算一次重疊區間再下結論，不要照抄。
- **這類上游「抓資料」的視窗問題，跟下游判斷邏輯（如本專案 2026-07-07 稍早修的 FilterEvents 跨日年假漏判）是兩個獨立層次，別混為一談**：下游過濾條件可能剛好正確排除了上游多撈的噪音，但「結果目前正確」不代表「上游查詢乾淨」——使用者指出「這筆不該出現」是合理要求，即使當下沒有造成錯誤決策，也該從源頭修。**但要先逐一驗證每支流程的下游邏輯，不能假設全部安全**：0945 剛好有「主旨含今天日期」AND 守衛擋住了張耀中案例（無害），但 1000/1010 的 FilterEvents **沒有**這層守衛（設計上信任抓資料層已經做好時間範圍、filter 端不重複判斷——這本身是合理的精簡設計），純靠姓名比對＋主旨含「10:00/全天」——這代表 Z 尾碼修正對 1000/1010 是**唯一防線、非選配**：沒套之前，任何人昨天請的單日全天假（主旨含「(全天)」）都會被誤判成「今天已請假」，是真的會發生的誤判，不是理論風險。「filter 不重複判斷時間」這個精簡原則要成立，前提是抓資料層必須先修乾淨——兩個修法互為前提，套一半是無效的。2026-07-07 使用者已在 Portal 套用兩項修法，確認 1000 流程正常執行。

## 2026-07-07（0945 請假判定：短時段請假=整天抑制，PO 已確認接受）
- **請假事件主旨含「10:00」即視為「涵蓋10:00」，不分請假時長**：`蔡宇翔請年假，2026-07-06(09:30-10:00)`（僅 30 分鐘）跟整天全天假一樣，都會讓 `本人請假`＝true→當天延遲信全部抑制、field_7 標「4. 延遲…當天已請假」。2026-07-07 使用者確認**接受此粗顆粒度**（不分長短假），非 bug——之後若又被提起「短假被當整天處理」，先查此條，不必重新當新 bug 診斷。

## 2026-07-07（指南寫法：fx 非必要步驟）
- **不必都點 fx 面板——欄位直接貼「已含 `@` 前綴」的完整運算式，失焦即自動變 chip**：2026-06-22 教訓「運算式必須用 fx 插入成 token，不可裸打」仍成立，但「怎麼帶上 @」不是只能靠點 fx 圖示、進面板打字——把運算式整段（含開頭 `@`）直接貼進欄位，一樣會被辨識成運算式。往後指南運算式一律附 `@` 開頭，指示文字寫「直接貼、免點 fx」，只有貼上仍是灰字才提示用 fx 修正。細節見 `rules/flow-guide-conventions.md`。

## 2026-07-06（SharePoint 委派不支援 Not/! 包函式；全域變數未初始化型別衝突）
- **`!IsBlank(x)`／`Not(IsBlank(x))` 對 SharePoint 連接器不可委派，改用 `x <> Blank()`**：委派警告明講「此連接器不支援 'Not' 作業」，邏輯等價的兩種寫法委派結果不同——`IsBlank()` 加 `Not`/`!` 包裝即不可委派，改成比較運算子 `<> Blank()` 就可以。舊公式（`ScrToday.galToday.Items`、`ScrAdmin.lblReply.Text`）長期用前者寫法未被注意，本次因整批檢查委派警告才浮現，屬既有但先前未修的問題，非新改動引入。
- **全域變數在 `Set()` 真正執行前引用會報「型別不相容：Text、Error」**：`Screen.OnVisible = Set(gToday, ...)` 是貼 YAML 貼不進去的手動步驟；控件公式裡的 `日期 = gToday` 在使用者手動加上 OnVisible 之前，`gToday` 型別未定會擋下整條比較式報錯。凡是引入「靠 OnVisible 手動設全域變數」這類修法，都要提醒使用者這一步是必要前置，不能只交付控件 YAML 就當作完成。

## 2026-07-05（多來源資料合併：欄位級去重優於列級優先序，backfill 前先確認基準是否已被人工改動）
- **「同 ID 取最高優先來源整列」的去重規則會讓空值蓋掉別處已有的真實值**：合併 清單.csv（即時匯出）與歷史工作表（週紀錄／月紀錄／歷史紀錄_現場查核）時，清單.csv 對某些日期已有該 ID 的「佔位列」但關鍵欄位（實際出勤狀態）還沒被下游流程填值，歷史工作表對同一鍵卻早有真實記錄；因清單.csv 整體優先序較高，整列取代後真實資料悄悄消失，且不報錯。**修法：對容易被下游延遲填值的欄位，改用「優先來源若該欄空白，改採其他來源的非空版本」的欄位級判斷，不能假設「來源優先序高＝該列每個欄位都比較準」**——來源優先序只該決定「同鍵衝突時預設信誰」，不該連帶覆寫掉優先來源恰好尚未填寫的欄位。
- **每人每日多列（per-task）但屬性是 per-person-per-day 時，合併/回填要做同鍵 fan-out**：實際出勤狀態本質是「一人一天一次」，但清單是「一人一天多任務列」，下游流程常只填到其中一列。合併多來源時若逐列各自判斷，會漏掉「同一天其他列已有值可以補」的情況；正確做法是先算出「同一鍵（Email+日期）內任一列是否有值」，有則 fan-out 補齊該鍵所有空白列，仍全空才視為真的無資料。
- **接續處理既有工作成果前，先確認對方是否已手動編輯，不能直接重跑原演算法覆寫**：資料合併分兩階段進行，第二階段開工前先讀取當下檔案狀態，發現列數比第一階段產出少了 38 列——排查後是使用者手動刪除了兩個國定假日（5/1、6/19）的占位列。若第二階段沿用「從原始來源重新生成整份分頁」的舊邏輯，會把使用者已判斷該刪除的列悄悄加回來。**正確做法：以當下檔案內容為基準做增量修補（本例僅改姓名格式、補狀態值），不整份覆寫重建**——這與「先 git status 再動手」是同一類紀律，資料檔案跟程式碼一樣要先確認現況再接手。

## 2026-07-05（日期欄格式零填補回填 + 跨平台 MM/mm 大小寫陷阱）
- **Power Automate `formatDateTime` 與 Power Fx `Text()` 的月/分鐘字母大小寫規則相反**：.NET 格式（Power Automate）`MM`＝月、`mm`＝分鐘；Power Fx（Power Apps）相反，`mm`＝月、`m`＝月（無零填補）、分鐘用 `n`。同一個「零填補月份」需求，Automate 端要打 `yyyy/MM/dd`，App 端 `Text()` 卻要打 `yyyy/mm/dd`——照抄字母大小寫會在其中一端把月份錯寫成分鐘（或反之），且不會報錯，只會靜默產生錯誤字串。跨平台複製格式字串前，先確認雙方的格式字元表，不能假設一致。
- **App 內用變數比對清單文字欄位時，變數格式須跟清單寫入格式逐字一致**：`日期 = gToday` 這類文字相等比對，只要兩邊格式字串有一絲差異（如零填補與否），比對永遠不成立，且**不會有委派警告或錯誤訊息**——表徵跟純委派問題一樣「抓不到資料」，但成因不同（格式不符 vs 不可委派）。改任一端的日期格式，另一端引用同一欄位的比對式必須同步改，否則等於引入新的一種「靜默抓不到資料」。
- **回填既有文字欄位優先從「已確定可靠的欄位」重新推導，不要解析待修正欄位本身**：清單「日期」欄本身格式不一致（單/雙位數混雜），若寫規則去解析它再重組，等於在不可靠輸入上疊加規則、更難保證正確；改用同一列裡另一個「已知格式固定」的欄位（本例＝`Title` 前 8 碼 `yyyyMMdd`，穩定且零填補）重新推導出新值最穩。
- **一次性回填用 Update／Patch（覆寫）而非 Add row（附加）**：本專案先前 TaskDB 備份流程用 append 累積、需額外防重跑機制；本次日期回填改用 SharePoint「更新項目」直接覆寫同一列同一欄，同值重跑不變、可安全重複執行，不必加防呆。兩種一次性/週期性寫入策略依「是否累積」選型，不要固定套用同一種。

## 2026-07-03（Power Apps 委派警告→兩週後抓不到資料）
- **`Text(Today(),...)` 包在 Filter/LookUp/UpdateIf 條件式內＝不可委派，且症狀有延遲潛伏期**：`Text()` 不在 SharePoint 可委派函式清單，條件式內出現即整條件退回本機運算（僅處理 App 非委派查詢列數上限內、預設 500 筆）。清單若採「append 累積不清空」策略，bug 在列數破上限前完全無症狀（成功運作兩週後才「突然」抓不到），排查時**別被「近期新變化」誤導去找 flow/清單改動，先查 App 畫面公式本身有沒有非委派函式**。
- **修法＝把非委派函式移出條件式，改比對預算好的變數**：開場（App.OnStart 或 Screen.OnVisible）`Set(gToday, Text(Today(),"yyyy/m/d"))`，Filter/LookUp/UpdateIf 條件式改純欄位＝變數比較，即可委派，不受清單列數成長影響。純顯示用途（標題列文字）的 `Text(Today(),...)` 不受影響、不必改。
- **委派警告三角形是唯一早期徵兆、資料量小時肉眼看不出異常**：養成「新公式一律檢查有沒有委派警告」的習慣，別等資料長大後才在生產環境爆出「抓不到資料」。

## 2026-07-02（0955/1005/1030 提醒流程設計）
- **全天行事曆事件的視窗要取單日**：全天事件（`isAllDay:true`）start/end 存 UTC 整天，與台北時區窗在午夜重疊；視窗取「昨天～明天」會把前天/昨天的全天假撈進來（實例：06-26 撈到 06-24 的假）。要「今天的假」→ 視窗＝今天 00:00–23:59（+08:00）＋主旨含今天日期守衛。
- **條件卡拿陣列比 true 恆 false**：`equals(body('filter'), true)` 永不成立（陣列≠布林），分支永遠走否——0955 既有流程即中此 bug（1/4 從不判仍逾期）。判「篩選有結果」用 `not(empty(body('filter')))`。
- **PatchItem 寫回後記憶體陣列是舊值**：迴圈內更新清單，先前 Get items 的結果不會跟著變；要拿「更新後狀態」做後續判斷（發卡名單），迴圈後必須重讀清單。
- **per-person 屬性存在 per-task 列時，判定用「任一列有值」**：field_8（出勤狀態）每人多列可能只填一列；判「已回報」＝Select email→union 去重→差集，不逐列判，避免誤提醒。
- **Select 對應式 `toLower(null)` 會炸整個 Select**：欄位可能空的一律 `toLower(coalesce(item()?['欄'],''))`，下游篩選再排空字串。
- **「參考某流程」先確認角色**：是「要改的主體」還是「只抄設定的範本」。使用者遞 1015 只為抄 Planner CreateTask 設定（GUID/指派寫法），非要重建該流程；能在既有流程尾端加動作就不另作新流程（使用者明確偏好）。
- **交付文件禁行銷式標籤**：不給概念貼口號（「兩軸分清楚」）；名稱/欄位/時段直述。使用者 2026-07-01 糾正。

## 2026-06-24 [Claude@Win]（Canvas gallery 逐列自動存 + 控件版本 + ai-team CLI on Windows）
- **gallery 內 OnChange 自動存「無限迴圈＋通知洗版」根因＝控件 Items 沒載入→Selected 變空→無 guard→不斷寫空值**：前版用未驗證的 `Classic/ComboBox`，陣列 Items 沒正常繫結→只剩預設「待確認」、Selected 空，OnChange 又沒擋空值→寫空→資料刷新→重算 Default→再 fire，無限循環。修法兩段：(1) 換「Items 穩定顯示」控件——`Classic/DropDown@2.3.1`＋`Items.Value: =Value`；(2) OnChange 三重 guard：`!IsBlank(Self.Selected.Value) && <>「（待確認）」 && <> 現值` 才寫。寫回後現值＝選值→guard 再為假→斷迴圈。雙控件（下拉＋自由文字欄）寫同一欄時各加同款 guard 即不互相覆蓋（文字欄寫自訂值→下拉 Default 落清單外→選取變空→`!IsBlank` guard 擋住，不會用空值蓋掉）。
- **gallery 逐列「目前值」用 `AddColumns(... As alias, Col, LookUp(...))` 在 Items 階段一次 join，別在每個控件 Default 內各自 LookUp**：每列重複 LookUp 不穩、易「全部顯示預設值」。Default 改讀 `ThisItem.<新欄>`。**巢狀 LookUp 內引用外層列必須用 `As` 命名**（`Sort(team_member,…) As tm` → `Email = tm.Email`）；寫 `ThisRecord.Email` 會指到內層 LookUp 的資料源而非外層列——Codex 建議就犯此錯，採納外部 agent 的程式碼要逐行守門。
- **pa.yaml 控件版本只用「使用者自己匯出裡出現過」的**：擅自挑 `Classic/ComboBox@2.4.0`（沒驗證）疑似沒正常繫結釀 bug。匯出實證可貼：`Label@2.5.1 / GroupContainer@1.5.0 / Classic/Button@2.2.0 / Classic/DropDown@2.3.1 / Gallery@2.15.0 / Rectangle@2.3.0`。清單沒有的控件優先改用已驗證控件達同效；要用就標「版本推測、貼不上換 PA 提示版本」。舊格式（無 @version）若該畫面已實證可貼（ScrToday＋Classic/Radio）就**原格式只改 style**，別為統一而轉新版引入版本風險。
- **Windows PowerShell 叫 codex/agy headless：長 prompt 含雙引號用 `$var` 直傳會被原生參數解析拆碎**（codex 報 `unexpected argument`、agy exit 255；PS 5.1 對含 `"` 字串的自動加引號會壞）。正解走 stdin：`Get-Content -Raw prompt.txt | codex exec -s read-only --skip-git-repo-check -`（`-` 讀 stdin、`-o out.txt` 收最終訊息）。agy 同理需 stdin/檔案餵入，直傳必壞。
- **ai-team 以 PO 硬需求否決 agent 建議**：Codex 主張「OnChange 不該寫 SharePoint、改加儲存鈕 Patch」，但使用者明示「不要儲存鈕」→ Tech Lead 採其對的部分（AddColumns 預 join）、否決加鈕，改以 guard 解迴圈。UpdateIf vs Patch：本資料模型每人每日多工作列、狀態複寫全列＝原設計語意，保留 `UpdateIf`（Codex 的 Patch 假設每人每日單列，不符）。

## 2026-06-22（Power Apps / Power Automate 平台踩坑彙整）
- **Power Automate 運算式必須用「fx 插入成 token」，不可在欄位直接打字**：直接打 `formatDateTime/concat/toLower/...` 會被當「字面字串」不計算（症狀：執行輸出出現整段運算式文字、或 Select 報「請輸入有效的 JSON」）。這是本次 0945 反覆卡關的真正主因。判斷：欄位裡是灰字＝字面(錯)、彩色 chip＝運算式(對)。**指南一律提供可整段貼的運算式，並註明「用 fx 插入」**。
- **SharePoint 清單欄位「內部名」≠ 顯示名**：CSV 匯入/中文欄常變 `field_N`（Email→field_3、姓名→field_4…）；運算式用顯示名 `item()?['Email']` 會回 null。**從「取得項目」一次執行的原始輸出 JSON key 即可確認對照**，別猜。Title、Email(若 ASCII)有時保留原名，但本案連 Email 都成 field_3。
- **Filter array 是「相對於迴圈值」過濾，不是原樣輸出**：「輸入有列、輸出卻空」＝where 對該列不成立（常是右側 `items('loop')` 值錯），不是該列有問題。**最快定位＝把比較一側寫死**（如 `equals(item()?['field_3'],'某email')`）跑一次：過＝右側(迴圈值)錯、不過＝左側(欄位)錯。
- **Select 文字模式(字串陣列) vs 鍵/值模式(物件陣列) 會改變下游 `items()` 型別**：兩者與消費端引用必須一致（字串用 `items('loop')`、物件用 `items('loop')?['key']`）。模式不確定時，`@or(equals(...,items()), contains(toLower(replace(string(items()),' ','')), '"key":"val"'))` 可同時涵蓋兩種。**但 Select 的值仍須是被計算的運算式**，否則兩種都不中。
- **低代碼某元件反覆搞不定時，換成更可靠的等價做法**：0945 的「Select 去重 email」屢卡 → 改用既有 team_member(Excel) 當人員名冊跑迴圈（姓名/Email 走 Excel header、清單只引 field_3），直接移除會壞的 Select。與行政頁簽同模式。
