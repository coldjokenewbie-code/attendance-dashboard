1. 專案目標與範圍

一句話：把「Planner 工作延遲 → 通知同事 → 同事回覆 → 行政查核出勤 → 歷史留存」這條每天早上跑的人工＋半自動流程，收攏成一個以 SharePoint 清單為單一真相源、Power Apps 為介面、Power Automate 為排程的系統。

環境MS365 Apps 商務版，10–50 人（實際名冊約 19 人）
上班制度預設 10:00–19:00；有 Planner 延遲工作者須 09:30 到公司早加班（詳見下方出勤規定）
出勤事實來源行政人員人工核對 ＋ 同事自行發「**信（米米信）」報備 ＋ Outlook 行事曆請假事件
核心價值行政不必再手工維護寬格式 Excel；同事在手機上自助查看與回覆；歷史可查

公司出勤規定2026-08-03 PO 口述，所有判定的依據

情境規定系統怎麼看
一般日 規定 10:00 到公司，但可以稍晚、也可以在其他地方工作。唯一義務是發米米信（主旨 ** 開頭）通知公司。 「10:00 沒進辦公室」不是異常；「沒發米米信」才是。所以 1005／1030 提醒看的是 field_8 有沒有值，不是人有沒有到。
當天有 Planner 工作延遲 必須提早於 09:30 到公司早加班，不可彈性遠端。 此時彈性上班的權利被取消，field_7 只能是「已完成」「已到公司早加班」「延遲未早加班（請填假卡）」「當天已請假」四種結局。
例外 當天 09:30 已在參與公司其他正式公出事項者，不受 09:30 到公司限制。 目前系統無此欄位，靠行政人工判斷後在出勤狀態註記。
兩軸不可混為一談：field_7 表單回覆＝延遲工作的處置（09:30 早加班軸，0945／0955／1015 管）；field_8 實際出勤狀態＝米米信與請假（10:00 到勤軸，1000／1010／1005／1030 管）。

範圍內

  • 個人出勤查核頁（今日延遲工作查看＋回覆）
  • 行政查核頁（全體當日一覽＋填實際出勤狀態）
  • 09:30–10:30 之間的 7 支排程流程（見 §7）
  • 清單 → Excel 的歷史備份
  • 請假紀錄查詢（模組二）、假期餘額查詢（模組三）未開工

範圍外

  • 請假申請：走公司既有外部表單，App 只放連結按鈕，不做申請邏輯。
  • LINE 發送：由既有 Windows 桌機程式 Planner2Line 監聽 Outlook 信件轉發，不在 Power Automate 內重做。
  • 行政人工核對本身：這是本質工作，系統只提供輸入介面，不取代判斷。

架構關鍵決定（歷史沿革，避免走回頭路）

  • 2026-06-16 架構反轉：原設計是「Excel 寬表為主檔 → 09:40 同步進清單」，已作廢。現行＝Planner 直接寫入清單，清單為工作區，Excel 只當歷史備份。Flow_0940_晨間同步與通知_建置規格.html 是反轉前的舊規格，不要照做。
  • 2026-06-08 決議重作 Canvas App，不修舊 App。舊 App 卡在 Popup 且已無人知道製作步驟。
  • 2026-07-06 個人／行政拆分（B 案）：行政查核獨立成另一支 Power App，解掉「行政要橫向表格、同事要手機直向」的版面衝突。ScrToday 已移除行政入口按鈕。
  • 儲存選型準則：唯讀、小量（<2000 列）、低頻 → Excel 直連（team_member、請假表）；多人並發寫、需權限、會累積 → SharePoint 清單（AttendanceHistory）。
  • 清單不每天清空：清單上限是 3000 萬筆，「5000」是檢視門檻不是儲存上限。每天清空會逼歷史查詢改讀 Excel（不可委派＋2000 列上限）反而更糟。改用保留期裁切（留一個月，見待決 A3）。

5. 資料模型

5-1. SharePoint List：AttendanceHistory單一真相源

運算式一律用內部名 field_N：中文欄位在 CSV 匯入時被改名，Power Automate 用顯示名會回 null。Power Apps（Power Fx）端則相反，用顯示名。
內部名顯示名格式／值域誰寫
TitleIDyyyyMMdd_Email_PlannerTaskId（延遲列）／yyyyMMdd_Email_TaskOnSchedule（占位列）0930 flow
field_1員工編號文字，0930 由 team_member join 補0930 flow
field_2日期單行文字 yyyy/MM/dd（零填補）0930 flow
field_3Email單行文字（不可用「個人或群組」欄型，比對會失敗）0930 flow
field_4姓名文字0930 flow
field_5方案名稱Planner 方案名；無延遲則空0930 flow
field_6任務名稱Planner 工作名；無延遲則空（＝占位列的辨識方式）0930 flow
field_7表單回覆存完整標籤字串，比對用 startsWith(...,'3.')同事（10:00 後唯讀）＋0955 收斂覆寫
field_8實際出勤狀態米米信主旨全文／請假事件主旨／行政下拉值僅行政＋1000／1010 flow，同事唯讀
field_9DateString樣本為空、不可靠；「今日」一律用 Title 前綴 yyyyMMdd_ 篩—

field_7 狀態機（同事在儀表板單選，5 選項）：

值語意0955 再巡檢怎麼處理
1.已完成（請自行勾掉卡片）查 Planner：真的不逾期→標「原勾選『1.』，同事已修改狀態」；仍逾期→歸 3. 並註記「卡片仍延遲」
2.延遲已到公司加班不動（明確排除，不發催填卡）
3.延遲（09:30 沒到公司，請填寫假卡）不動；最終 field_7 開頭是「3.」＝仍延遲＝要發 Planner 催填卡片
4.延遲（09:30 沒到公司，當天已請假）同 1.：查 Planner 實況
5.其他（自填）—
（空白）沒回覆應同樣查 Planner 是否仍逾期（此修法已寫、待套用）
Title 不可用 Split(x,"_") 解析：Planner task id 是 28 字元 base64url，結尾可能就是底線（實例 …vXu-m6GEu0amsGMCTVsn5skAK6t_），取最後一段會靜默拿到空字串。要取 task id 用 Mid(Title, Len(Email) + 11)，更好的做法是讓 0930 flow 多寫一欄 PlannerTaskId。

6. 功能模組規格

模組一 A：個人出勤查核頁 ScrToday 已上線

  • 資料：Filter(Filter(AttendanceHistory, Email = User().Email, 日期 = gToday), 任務名稱 <> Blank())——內層可委派條件下推伺服器、外層本機處理數筆。
  • 版面：手機優先、單欄直向、整頁可捲；Gallery 卡片顯示【專案】【工作】【回覆】【實際出勤狀態】。所有 Label 開 AutoHeight、Y 座標串接（引用上一個控件的 Y + Height + 間距）。
  • 回覆 Popup：點卡片按鈕開 Popup，5 選項單選，寫回 表單回覆。
  • 時間鎖：radReply.DisplayMode／btnSubmit.DisplayMode＝If(locIsAdmin Or Hour(Now())<10, Edit, View)；btnSubmit.OnSelect 內再驗一次（DisplayMode 只擋畫面，Patch 要自衛）。
  • 已知代價：垂直 Gallery 列高無法逐列自動，TemplateSize 只能取最壞情況（現 420），短內容會留白。

模組一 B：行政查核頁 ScrAdmin 修法待貼上

  • 獨立 Power App（非同 App 的另一畫面），桌機橫向、關閉 Scale-to-fit。
  • 版面：一頁 25 列全覽的表格，TemplateSize = (Parent.Height - 116) / 25；4 欄＝員工編號｜姓名｜出勤狀態（已存＝粗體藍）｜行政輸入下拉＋自訂文字｜今日延遲工作與同事回覆。
  • 人員來源：AddColumns(Sort(team_member, 員工編號) As tm, CurStatus, LookUp(...)) —— 在 Items 階段一次 join 現值，不在每個控件 Default 各自 LookUp。
  • 自動存（無儲存鈕，PO 硬需求）：下拉 OnChange 三重 guard 才寫入——非空白 ＆ 非「（待確認）」 ＆ 與現值不同。缺 guard 會無限迴圈洗版。
  • 長文字處理與 ScrToday 相反：本頁要一頁全覽，所以 Wrap: =false 單行截斷＋Tooltip 看全文（代價：只能桌機用，手機沒有 hover）。
  • 權限閘：Screen.OnVisible 算 locIsAdmin，內容容器逐個綁 Visible = locIsAdmin＋全螢幕遮罩雙保險。
// Screen.OnVisible（pa.yaml 帶不進畫面屬性，貼完必須手動補回）
Set(gToday, Text(Today(), "yyyy/mm/dd"));
UpdateContext({locIsAdmin:
  Trim(Coalesce(LookUp(team_member, Lower(Email) = Lower(User().Email), '出勤存取權限'), "")) = "行政管理"});
ClearCollect(colToday, Filter(AttendanceHistory, 日期 = gToday))
權限判定不能用 !IsBlank(LookUp(...))：Excel 空欄回傳空字串 ""，IsBlank("")＝false，會讓名冊裡每個人都被判成行政。必須改值比對。

9. 平台限制與設計約束

Power Apps / Power Fx

  • 委派：Text()、Not()／! 包函式對 SharePoint 不可委派。!IsBlank(x) 改 x <> Blank()；Text(Today(),...) 改在 OnVisible 算成 gToday 變數再比對。改不掉的條件用巢狀 Filter（外層放不可委派的、內層只留可委派的）。
  • 非委派查詢的資料列限制（App 設定→一般，預設 500、最大 2000）：本機模式只取清單前 N 列（依 ID 遞增＝最舊），症狀必然是「最新資料抓不到」而非「全部抓不到」——這個方向性是辨識此類 bug 的指紋。
  • 垂直 Gallery 列高固定，無法逐列依內容自動。
  • Label 固定 Height 在手機上必裁長文字；長度不可控的 Label 一律 AutoHeight: =true，下方控件 Y 引用它的 Height。
  • Screen.OnVisible 是畫面屬性，pa.yaml 貼不進來，每次全選重貼都要手動補回。
  • pa.yaml 貼上是控件層級、一次一畫面；兩個畫面塞同一檔會 PA1001。控件版本只用「使用者自己匯出裡出現過」的：Label@2.5.1 / GroupContainer@1.5.0 / Classic/Button@2.2.0 / Classic/DropDown@2.3.1 / Gallery@2.15.0 / Rectangle@2.3.0。
  • Excel 空欄回傳 "" 不是 Blank()，判「有沒有填」不能用 IsBlank，要比對值。
  • Visible 是畫面層、非安全邊界。

Power Automate

  • 運算式必須是 token 不是字面文字：欄位裡灰字＝字面（錯）、彩色 chip＝運算式（對）。整段貼「已含 @ 前綴」的運算式，失焦即自動變 chip，不必先點 fx。
  • 新版「條件」卡沒有進階模式：布林先用 Compose 算，條件只比 = true，且右值的 true 要用 fx 插成布林（直接打字會變字串 'true'，永遠不成立）。
  • Set variable 禁止自我參照，累加陣列改用「附加至陣列變數」。
  • OData $filter 用內部欄名；中文／改名欄會報「欄不存在」。Title 內部名固定，日期範圍一律用 startswith(Title,'yyyyMMdd_')，不對 日期 欄下 $filter。
  • 時區：某些環境 convertFromUtc(...,'Taipei Standard Time') 報無效，備案 addHours(utcNow(),8)。行事曆全天事件錨定 UTC 午夜，查詢視窗尾碼要用 Z 不是 +08:00，否則會撈到昨天的假。
  • 格式字元大小寫兩平台相反：Power Automate MM＝月、mm＝分鐘；Power Fx mm＝月、分鐘用 n。照抄會靜默寫錯。
  • PatchItem 寫回後記憶體陣列仍是舊值，要拿更新後狀態做後續判斷必須重讀清單。
  • 接手既有流程先解壓匯出的 definition.json，別靠 designer 表象或記憶猜 action 名稱。

SharePoint 清單

  • 比對鍵欄位（Email）必須是單行文字，不可用「個人或群組」。
  • 排序／識別鍵一律用零填補固定寬度字串（yyyyMMdd），文字序才等於時間序。
  • 破 5000 列後，未編索引的欄位即使查詢可委派也會失敗 → Email、日期 需加索引。
